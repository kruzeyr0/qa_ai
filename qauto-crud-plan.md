# QAuto CRUD Test Plan

## 1. Objective

Validate the QAuto API CRUD lifecycle using one-time synthetic data:

- create a synthetic user;
- read the created user;
- update the user profile;
- obtain car reference data;
- create a car for the synthetic user;
- read and update the created car;
- delete the created car;
- delete the synthetic user.

The collection also contains one negative scenario and one boundary scenario.

## 2. Test Data

All test data is synthetic and intended for one test run only.

### User

- `name`: generated synthetic value
- `lastName`: generated synthetic value
- `email`: generated uniquely for each run
- `password`: generated test password
- `repeatPassword`: same as password

The email is generated by the collection at runtime and stored in the `testEmail` collection variable. The created `userId` is stored in `testUserId`.

### Car

- `brandId`: obtained from `GET /cars/brands`
- `modelId`: obtained from `GET /cars/models` and selected for the chosen brand
- `mileage`: value suitable for the normal create-car scenario
- `carId`: obtained from the create response and stored in `testCarId`

The collection does not contain real user credentials or LMS credentials.

## 3. Scenario Sequence

### Happy Path / CRUD

1. **Create User**
   - `POST /auth/signup`
   - Expected: successful user creation.
   - Save returned `userId`.

2. **Read User**
   - `GET /users/current`
   - Verify HTTP `200`.
   - Verify returned `userId` matches the created user.

3. **Update User**
   - `PUT /users/profile`
   - Verify HTTP `200`.
   - Verify successful update response.

4. **Get Car Brands**
   - `GET /cars/brands`
   - Verify HTTP `200`.
   - Verify the returned list is not empty.
   - Save a brand ID.

5. **Get Car Models**
   - `GET /cars/models`
   - Verify HTTP `200`.
   - Verify the returned list is not empty.
   - Select a model belonging to the selected brand.

6. **Create Car**
   - `POST /cars`
   - Create a car using the selected brand, model and valid mileage.
   - Save returned `carId`.
   - Verify returned brand/model match the request.

7. **Read Car**
   - `GET /cars/{carId}`
   - Verify HTTP `200`.
   - Verify returned car ID matches the created car.

8. **Update Car**
   - `PUT /cars/{carId}`
   - Increase mileage by 500.
   - Verify HTTP `200`.
   - Verify mileage was updated.

9. **Delete Car**
   - `DELETE /cars/{carId}`
   - Verify HTTP `200`.
   - Verify the deleted car ID matches the created car.

10. **Delete User**
    - `DELETE /users`
    - Verify HTTP `200` and successful response.
    - Remove remaining user-related collection variables.

## 4. Negative Scenario

### Signup with a Required Field Missing

Request:

- `POST /auth/signup`
- `lastName` is intentionally omitted.

Expected behavior:

- HTTP `400`;
- response status is `error`;
- response contains an error message;
- no user data is returned;
- no persistent user is created.

The email for this negative scenario is generated as a local variable so it is not reused as persistent test data.

## 5. Boundary Scenario

### Mileage Above Maximum

Request:

- `POST /cars`
- mileage is set to `1000000`.

The documented maximum is `999999`, so the test sends a value one unit above the maximum.

Expected behavior:

- HTTP `400`;
- response status is `error`;
- response contains an error message;
- no car is created.

This scenario depends on valid brand and model IDs obtained from the preceding reference-data requests.

## 6. Dependencies

The scenarios have the following dependencies:

- `Get Current User` depends on successful `Create User`.
- `Update User` depends on the authenticated user created by Signup.
- `Get Car Models` uses reference data obtained from the API.
- `Boundary Case` depends on valid `testCarBrandId` and `testCarModelId`.
- `Create Car` depends on valid brand/model IDs.
- `Read Car`, `Update Car`, and `Delete Car` depend on the `carId` returned by `Create Car`.
- `Delete User` is executed after `Delete Car`.

## 7. Cleanup Strategy

Cleanup is performed in dependency-safe order:

1. Delete the created car.
2. Delete the created user.
3. Unset collection variables related to the deleted entities.

The negative and boundary scenarios are expected not to create persistent entities, so they do not require separate cleanup.

## 8. Stop Criteria

Stop the scenario if:

- user creation fails and no valid `userId` is available;
- authentication/session state is not established;
- required car reference data cannot be obtained;
- a required dependency for creating the car is missing;
- cleanup cannot be performed safely;
- Swagger/API documentation and actual behavior conflict in a way that makes further execution unsafe.

If an individual assertion fails but the created entity remains usable and cleanup can still be performed safely, continue the CRUD chain and record the failure as evidence.

## 9. Expected Evidence

The execution evidence should record:

- number of requests and tests;
- passed/failed assertions;
- actual HTTP status codes;
- results of the negative and boundary scenarios;
- CRUD results;
- cleanup results;
- any mismatch between expected and actual API behavior.

The executed run is expected to preserve a detected status-code mismatch in the Create Car assertion rather than silently changing the test expectation.
