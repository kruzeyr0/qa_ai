Виконай підготовчий етап для API-тестування навчального застосунку **Hillel Auto (QAuto)**.

### 1. Отримання OpenAPI-специфікації

Завантаж JavaScript-файл:

https://qauto.forstudy.space/api-docs/swagger-ui-init.js

Сайт закритий через HTTP Basic Auth. Дані доступу є навчальними, спільними для групи та знаходяться в інструкції LMS.

Використай ці credentials для HTTP-запиту, але:

* не записуй їх у жоден файл;
* не додавай їх до OpenAPI JSON;
* не додавай їх до Postman collection;
* не додавай їх до environment/config-файлів;
* не виводь credentials у результаті роботи;
* не коміть жодних credentials.

У JavaScript-файлі знайди об'єкт **`swaggerDoc`** та витягни **саме його**, без іншого JavaScript-коду.

Збережи отриману специфікацію як валідний JSON-файл:

`hillel-auto-openapi-<сьогоднішня дата>.json`

у поточну теку.

Після збереження перевір, що JSON синтаксично валідний і містить OpenAPI-специфікацію.

Покажи:

* розмір створеного файла;
* кількість операцій у `paths`;
* перелік усіх `paths` із HTTP-методами.

Нічого не коміть і не створюй commit.

### 2. Підготовка динамічних тестових даних для Postman

На основі отриманої OpenAPI-специфікації підготуй логіку для подальшої CRUD Postman collection.

Для тестового користувача **не використовуй статичний email**.

Створи Postman-логіку, яка при кожному новому запуску CRUD-сценарію генерує унікальний synthetic email, наприклад:

`qa.<timestamp/random>@example.com`

Важливо:

* email має бути гарантовано унікальним для кожного запуску;
* він не повинен містити реальних персональних даних;
* згенерований email має зберігатися у Postman variable;
* усі наступні запити, яким потрібен email користувача, повинні використовувати саме цю variable;
* не генеруй новий email перед кожним окремим HTTP-запитом.

Потрібна така логіка життєвого циклу:

`Generate email → Save variable → Create User → Use same email in subsequent requests → Cleanup/Delete User using the same saved email or associated user ID`

Якщо API після створення користувача повертає `userId` або інший ідентифікатор, збережи його у Postman variable та використовуй для наступних операцій і cleanup.

Для cleanup не створюй новий ідентифікатор і не генеруй новий email — потрібно видалити **саме ту synthetic-сутність, яка була створена під час поточного запуску**.

Перед реалізацією перевір у Swagger:

* які поля необхідні для створення користувача;
* який endpoint використовується для створення;
* який endpoint використовується для видалення;
* чи використовується email або ID для видалення;
* які status codes документовані;
* які response fields можна використовувати для збереження ID.

Якщо Swagger не містить необхідної інформації для безпечного cleanup або фактичний API-контракт суперечить документації, **не вигадуй поведінку API** та зафіксуй це як blocker.

На цьому етапі не виконуй destructive-операції над чужими даними.

### 3. Безпека

Використовуй виключно synthetic одноразові тестові дані.

Не використовуй:

* реальні email;
* реальні паролі;
* персональні дані;
* credentials з LMS у файлах;
* credentials у Postman export;
* access tokens або Basic Auth credentials у фінальних артефактах.

Нічого не коміть.

Наприкінці покажи короткий підсумок:

1. OpenAPI-файл створено;
2. JSON валідний;
3. кількість операцій;
4. список paths;
5. які variables потрібні для CRUD;
6. як генерується та зберігається унікальний email;
7. як забезпечується видалення саме створеного користувача;
8. чи є blockers.
